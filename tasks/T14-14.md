# T14-14  Exceptions

## Inputs
- Exceptions list
- configuration `policy.exceptions`

## Outputs
- hourly scheduled job: approved exception to configuration
- renewal reminder flow
- expiry check in `box policy validate`

## Steps
1. An approved Exceptions item becomes a `policy.exceptions` entry, saved by the pipeline app as a new configuration version with one Events item: `id` from `requirement_id`, `reason`, `reference` from `exception_id`, `ends` from `expires_on` (SPEC §23). An exception added in the TUI creates its Exceptions item.
2. Thirty days before `ends`, a scheduled flow asks the approver to renew or close; an expired entry fails validation and the setting returns on the next apply.
3. Scope: the configuration entry has no scope, so an exception removes its setting for everyone. Applying a user, group or device scope as an exclusion group needs a scope field in `policy.exceptions`; propose it in docs/spec-changes.md and stop before building it.

## Human steps
- None.

## Exit criteria
- An expired exception fails `box policy validate` and `box config validate`.
- An exception approved on the list appears in the configuration and on the Review screen.
- Every exception change has one Events item.

## Evidence
- Engine: front matter `status: DONE` with the commit reference. Tenant: the step's `Setup` list item and evidence artefact (SPEC §14).
