Answer: **yes for discovery and device-code sign-in**. Browser sign-in
with PKCE could not be exercised from the cloud container. It moves into
T0-04's exit criteria, to be run on the owner's machine.

## Sign-in

- **Device code** works with the Graph Command Line Tools client. The
  admin consented to every bootstrap scope at sign-in. Tenant default
  policies did not block device-code sign-in.
- On iPhone Safari, one attempt failed with **AADSTS165000** ("user session
  context is missing"). Safari lost Microsoft's sign-in cookies part-way
  through. A fresh attempt in a normal Safari tab succeeded. The TUI's
  sign-in guide must say: use a normal (not private) browser window, open
  the address directly, and finish without switching apps.
- A device code is single-use and tied to the process that requested it.
  If the user signs in with an older code, the waiting process sees
  nothing. The TUI must show only one live code and cancel the old one.
- Browser sign-in with PKCE on `localhost`, on Windows, macOS and Linux,
  remains to be verified on a desktop. That is now an exit criterion of
  T0-04.

## Consequences

- Discovery maps `skuPartNumber` to plans with `engine/capabilities.yaml >
  skus`. `SPB` maps to business_premium.
- Security defaults are on in new tenants. T1-05 turns them off only after
  Conditional Access policies CA01 and CA02 are on (unchanged plan).
- The delegated scope `Policy.Read.All` was added to the bootstrap scopes,
  for the security-defaults and Conditional Access reads.
