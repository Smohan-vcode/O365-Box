# T14-18  Edge extension requests: staff ask, the owner decides

With the choice `devices.browser_extensions` = `approved`, Microsoft Edge
blocks every extension (`ExtensionInstallBlocklist` `*`) except the allow
list. This task gives staff a way to ask for one and the owner a way to
decide, without a premium connector (R2) and without the box ever adding
an extension on its own (SPEC §25).

## Inputs
- register list `ExtensionRequests` (engine/register/lists.yaml): extension
  id, name as the requester knows it, store name, reason, requester, asks
  for everyone, state `requested | approved | rejected`, decided_by,
  decided_at, decision reason
- configuration `devices.browser.extension_allowlist` (schema: 32 letters
  a to p, unique), the one home of the approved list (R11)

## Outputs
- step `sharepoint.extension-requests`: the list's form for staff
  (`<Admin site>/Lists/ExtensionRequests/NewForm.aspx`); staff add requests
  and read only their own (item-level read 2), with a permission level that
  has no edit right; the decision columns are left out of the form; the
  state defaults to `requested`
- `box extensions requests [--all]`, `box extensions request <id> --by`
  (on behalf of a person), `box extensions approve <number>
  [--install-for-everyone]`, `box extensions reject <number> --reason`
- home screen card "Requests waiting for you" (`tui.Options.Requests`,
  `DecideRequest`): `a` approve, `i` approve and install for everyone,
  `x` turn down with a reason
- mappings: WIN-069 and MAC-030 read `{list:devices.browser.extension_allowlist}`;
  MAC-030's block list reads `{list:edge_extension_blocklist}` from the
  choice, so `store` leaves only the extension lists out (not the rest of
  the Edge settings); Windows payloads expand `{list:x}` and leave out a
  setting whose list is empty

## Steps
1. Staff fill the form: extension id (from edge://extensions with
   developer mode on), its name, why. No flow is needed: the owner sees the
   request on the home screen or with `box extensions requests`.
2. The owner approves or rejects. An approval checks the id (32 letters a
   to p), looks up the store name only if the Edge Add-ons store answers
   (otherwise the id and the requester's description are shown), writes
   the id into `devices.browser.extension_allowlist` (validated before it
   is written; the rest of the document is kept line for line), marks the
   item approved with decided_by and decided_at, and writes one `Events`
   item. If the item cannot be marked, the configuration is restored.
3. The configuration change is a new version: `box plan --proposal --only
   sharepoint.config-store,policy.intune-windows,policy.intune-macos`, then
   `box approve` and `box apply`. Nothing reaches a device before that.
4. A rejected or approved request is never decided again; the list's state
   column alone allows nothing (an item a person marks approved in the
   list is not in the configuration).

## Human steps
- None. The owner's decisions are the product's normal approvals.

## Exit criteria
- `box check sharepoint.extension-requests` passes on the test tenant.
- On the test tenant a sample request (a public store extension id) is
  approved with `box extensions approve`, the proposal for
  `policy.intune-macos` shows the allow list change, and after approve and
  apply `box check policy.intune-macos` passes with the id in the Edge
  allow list.
- `go test ./...` covers the id check, the in-place configuration edit, the
  restore on a failed decision and the home screen card.
- A second apply plans no changes.

## Evidence
- Engine: front matter `status: DONE` with the commit reference. Tenant:
  the request item, its Events item, the configuration version and the
  step's `Setup` list item (SPEC §14).
