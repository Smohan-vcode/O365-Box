# T13-09  Choices engine

## Inputs
- SPEC §24
- defaults/choices.yaml
- expected-state/setting-ids/*.json

## Outputs
- schema: `choices` section; `box config validate` checks choice ids, options and `when`
- resolver applies choices (modules, variants, exceptions) before tier and exceptions
- `box choices list|show <id>` (headless parity)
- setting variants in expected-state/setting-ids (variant keys named by choices)

## Steps
1. Load and validate defaults/choices.yaml: unique ids, known steps, options with labels and costs, effects naming known modules, settings, bundles and gates.
2. Add variants to the mappings of the settings that choices select (WIN-058, MOB-005, DEF-013, ADM-003, ADM-010, OFC-011) and a check that every variant a choice names exists.
3. Apply choices in the resolver; report which choice left a setting out, like an exception.
4. Default every unanswered choice to its recommended option (or `recommended_when`), and show that in the plan.

## Human steps
- None.

## Exit criteria
- The test tenant's configuration expressed as choices resolves to the same applied settings as today (302).
- An unknown option or a variant without a mapping fails validation, naming it.
- Changing one choice changes only the settings it names in `box plan`.

## Evidence
- Engine: front matter `status: DONE` with the commit reference. Tenant: the step's `Setup` list item and evidence artefact (SPEC §14).
