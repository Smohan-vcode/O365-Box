# T14-04  Apply engine with audit and enforce modes

## Inputs
- SPEC §14, §20, §23
- expected-state/setting-ids.json
- configuration `policy.rollout` and `policy.exceptions`

## Outputs
- provider steps `policy.<area>` (test, plan, apply, verify, evidence)
- commands: box apply policy.<area>, box check policy.<area>

## Steps
1. One step per area, run by the orchestrator with the pipeline app: `plan` compares the resolved settings with the tenant; `apply` writes them from the resolved ids; `verify` reads each setting back.
2. Mode audit maps to the product's own mechanism: report-only for Conditional Access, audit for attack surface reduction, test with notifications for data loss prevention, assignment to `policy.rollout.pilot_group` for device policies.
3. Mode enforce assigns to all users on a covering plan, always excluding `grp-break-glass` where the product allows (SPEC §20.2). Refuse to enforce a blocking Conditional Access policy unless `box check break-glass` passes in the same run.
4. Changing `policy.rollout.stage` plans changes to staged settings only.
5. Write one PolicySettings item per setting with its live state, update each Requirements item's status, and write evidence per requirement.
6. Move each provider step that reads a file in baseline/ (identity, exchange, sharepoint, teams, devices) onto the resolved settings; delete the file when nothing reads it (SPEC §4).

## Human steps
- None.

## Exit criteria
- `box check policy.<area>` reports every applied setting as matching on the test tenant.
- Switching `rollout.stage` to enforce changes only staged settings.
- A second apply plans no changes.
- No blocking policy is enforced while `box check break-glass` fails.
