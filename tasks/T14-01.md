# T14-01  Resolver, validation and coverage

## Inputs
- SPEC §20.1, §23
- policy/ (requirements.yaml, settings/, frameworks/, capabilities.yaml)
- configuration `policy` section; examples/acme/ for tests

## Outputs
- engine/internal/policy: resolver, validation, coverage
- command: box policy resolve
- command: box policy validate
- command: box policy coverage

## Steps
1. `box policy resolve`: from the catalogue, the configuration's `policy` section and the plan's capabilities (from discovery; `tenant.default_plan` when headless), keep a setting when its capability is on the plan, its tier is selected and no exception removes it. Output, per area, the settings to apply with their mode, the settings not applied with the reason, and the requirement status. Deterministic; printed or `--json`; never written into the repository.
2. `box policy validate`: every setting names existing requirements and a known capability; every technical requirement has a setting; every framework control names existing requirements; ids are unique; every exception has `id`, `reason`, `reference` and `ends`, names a known setting or requirement, and has not expired. `box config validate` runs the exception checks too.
3. `box policy coverage`: for each selected framework, control by control, the requirements enforced by settings, by procedure, needing an add-on and not selected; the plan's users not covered (from T14-02 once it exists).
4. Tests with a fixture for each validation failure, and a resolve of `examples/acme/` with a golden result.
5. CI: run `box policy validate` on every pull request; post the coverage summary for `examples/acme/` as a pull-request comment when `policy/` changes.

## Human steps
- None.

## Exit criteria
- Resolver output is identical on two runs.
- Each fixture fails with a message naming the item.
- An expired exception makes `box config validate` exit 2.
- After `box policy resolve` and `box policy coverage` the working tree is unchanged.
- `box check-literals` passes on `policy/`.
