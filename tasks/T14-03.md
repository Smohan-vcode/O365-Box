# T14-03  Setting resolution

## Inputs
- policy/settings/*.yaml
- spikes/findings (S-02) and expected-state/baseline-coverage.yaml
- expected-state/app-permissions.yaml

## Outputs
- expected-state/setting-ids.json
- each area assigned to a provider and declared as a step in that provider's steps.yaml

## Steps
1. For each setting, find the exact API object: Conditional Access policy definition; settings-catalogue or endpoint-security definition and value in Intune; attack surface reduction rule identifier; cmdlet and parameter in Exchange, SharePoint, Teams, Purview and Power Platform; organisation setting in Graph.
2. Record id, API path, payload and read-back check in expected-state/setting-ids.json, keyed by setting id. Record whether S-02 shows the Tenant Configuration Management APIs can write or monitor it.
3. Assign each of the 12 areas to an existing provider (identity, exchange, sharepoint, teams, intune, powerplatform); add a provider only where none can reach the API.
4. List the permissions and Entra roles the steps need. Where one is not in expected-state/app-permissions.yaml, propose the addition in docs/spec-changes.md and stop; never grant it.
5. Where the product has no setting that delivers the stated value, do not approximate: record it as unresolved with what is available, and stop for a decision.
6. Where a setting is only possible in a portal, define it as a gate (SPEC §22, R5) with a guide, its expected value and a check.

## Human steps
- Decide each unresolved setting: reword the requirement, accept a nearer setting, or record an exception.

## Exit criteria
- Every applied setting is resolved, a gate, or unresolved with a reason.
- No setting is resolved to a capability outside the plan.
- Every permission the steps need is in expected-state/app-permissions.yaml or proposed and not granted.
- A second run changes nothing.

## Evidence
- Engine: front matter `status: DONE` with the commit reference. Tenant: the step's `Setup` list item and evidence artefact (SPEC §14).
